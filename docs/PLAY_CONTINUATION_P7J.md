## 完成の定義：機能テストPASSではなく実機での循環PASS

ユーザーがiPhoneから現在画面を1回送る → Navigatorが既存画像と履歴を再利用し、現行状態の候補を比較 → `next_action.py` と `check_reply.py` のPASSを満たす操作をひとつ提示 → ユーザーがゲーム内で手動実行 → 結果を現行ブランチへ取り込み → 次の手を提示。ユーザーをCodexとChatGPT間のメッセージ中継役にしない。

最初の受入れは【特訓1回＋結果反映＋次の操作判定】を実機で完走すること。通常プレイ復帰の受入れは、少なくとも異なる行動種別（特訓以外に試合または校内活動、必要なら回復）を含む二つ以上の連続した実機サイクルで、古い選手画像を要求しないこと。選択・実行はユーザーのiPhone上で行い、AIはゲームを自動操作しない。

## 最重要の設計差分（現行とのギャップ）

1. `navigator_step.py` は UNKNOWN 時に自由文の `development_plan` を先に要求し、単一の指定された特訓だけを優先比較している。過去の参加者固定組み合わせを全候補の代わりにしてはいけない。
2. `next_action.py` と `check_reply.py` は特訓の認証済み文章のみを描画できる。試合・校内活動・回復が比較上有望でも `RENDERING_UNSUPPORTED` で止まる。この現実の停止原因を所有者側で修正する。
3. ロスター原画像とタイプ×相性データは存在するが、現在の画面と非公開証拠の受け渡しはまだ一連の自動導線になっていない。 `NEXT_ACTION_P7H.md` の現行 `private-context` と `private-evidence-index` を使い、公開GitHubのP4 bridgeへスクリーンショット、個人情報、私有ファイル位置を送らない。
4. `CERTIFIED_TRAINING_DRAFT` は現状「手動承認前の下書き」であり、それだけでは遊べたことにならない。ユーザー自身のゲーム内「実行」操作を明確な人間の受入れ境界とする表示について、既存契約に照らして実装・検証する。安全性の判定や正確な文面認証を省略しない。

## 1. 入力：同じデータを聞き直さない

入力は `CURRENT_LIVE_STATE.json` / `LIVE_EVENTS.jsonl`、現行ロスターの原本SHA、保存済みタイプ表・相性表、必要最小の現在画面、当該ゲーム操作の結果。

保存情報は3種類へ分類：
- **安定観測**：選手名・タイプ・ロスター能力・既知の特訓費用・機構上の相性対応。元の画像SHA・観測時点を保持し、当該SAVEで選手情報が変わった証拠がない限り再提出不要。
- **変化し得る現行観測**：選択中の特訓、参加者、HP、残スポーツP・応援、アイテム在庫、試合日程など。何が変わったかに応じて該当フィールドのみ鮮度を失う。時刻の自然進行とSAVEの切替は区別する。
- **過去の検証知識**：4回目のスキル画面、過去の相性45%、公開のスキル補正値。育成優先順位の根拠として参照できるが、現在SAVEのスキル・回数・発動確定値に昇格させない。

既存 `IMG_9038(1).png` SHA `bfced92c21b00e2069738eaf51827f13e6a7feeac2eb6a67386232ff7277613f` と `IMG_9039(1).png` SHA `8f532e93c97e0dae91c010fb17f1d1d570dd1187a4b9bc3da5fe67a906d804b5` は現行SAVEとユーザーが報告。これらは過去のキャプチャ時点の残高を示す。実行直前の残高である保証は別途必要。旧ロスターZIP `6ec60a855270aa1243c25ccb9ca6d0ed90a00d7073b3f7572fe9026f1686945e` を使い直し、二重提出を求めない。

証拠不足時の問い合わせは、実行候補に本当に必要な不明項目だけに限定する。一度にひとつの無消費の確認操作か現在画面を指定し、既に確認済みの質問を繰り返さない。SAVE/LOAD・特訓・試合・アイテム使用では必要な鮮度だけを再評価する。

## 2. 判断：候補をすべて比較し、1手だけ選ぶ

候補生成の単位：行動種別 × 特訓種別 × 参加者3名 × 応援ON/OFF、または現在実行可能な試合、資源目的が証明された校内活動、必要性が証明された回復。利用不可の行動は、歴史的に存在していても実行候補に含めない。

各候補に、(a) 10月に必要な役割と戦力上昇、(b) 実測の直接能力上昇（範囲/不明を許す）、(c) タイプによる特訓相性と実際の適用条件、(d) スキル獲得機会・4回目進行・装備4枠、(e) 特訓レベル進行、(f) 消費スポーツP/応援/HP/期間、(g) 次試合・月末ゲートへの影響、(h) 出典と確実性を持たせる。

`SKILL-4TH-PATTERN` は候補価値の大きな要因。現在SAVEの選手×特訓に **正本で確定した3回** があれば4回目候補として重視するが習得を保証しない。未確定回数は0回扱いしない。現行SAVE未確認の効果+30/+100/+150は「将来獲得可能性のある参考効果」であり、確率・Lv1習得保証・現在装備能力には換算しない。応援ONがスキル確率を上げるとは仮定しない。

順位決定は架空の期待得点や固定重みを使わない：
1. **実行可否**（ACTIVEルール・イベントrevision・現行画面・費用・日付・実行可能性）を確認。
2. 期限上の必須行動／既に証明された戦力上のボトルネックを先に満たす。
3. 同じ目的の候補間で、根拠のある優越関係（他の重要条件で劣らず、ひとつ以上で優る）を判定。
4. トレードオフが残る場合、10月までに有効な主力スキルへの進行 → 直接能力と成長 → 実証された相性 → 消費の少なさ、の説明可能な順で比較。ただしこの順番は絶対的なスコアではない。高価値の別試合・回復や直近公式戦を無視しない。
5. 最優先が決まらず、実行に影響する根拠が不足する場合は、その根拠を取得するための無消費確認をひとつだけ返す。

相性表は既存 Authority の `drill_affinity_full` と送付済み選手タイプを照合。過去の「ティーバッティング45%」を、未観測の現行「素振り45%」として表示・適用しない。

## 3. 状態と停止条件：全件停止をやめ、誤操作は防ぐ

- **実行可**：選択中候補に必要な全フィールドが現行SAVEから証拠付きで一致。 `validate_recommendation` / `validate_skill_recommendation` と実際の `check_reply` がPASS。
- **候補の比較は可能／操作保留**：獲得確率、歴史的特訓回数、別系統の在庫、別試合の結果など、選択中の操作に無関係なUNKNOWNは比較に残しつつ、現行操作の認証まで広げない。現行操作に必要な費用・選手・SAVE枝が不明なら実行しない。
- **停止**：SAVE不一致、状態変更を反映していない入力、費用不足、必須証拠欠落、同期不一致、ルール抵触、公式戦等の不可逆な人間判断。毎回 `blocking_reason` と `resolve_by` の組を最大限具体的に示す。
- 現行SAVEに確定回数がないまま4回目のスキル再抽選を指示しない。REJECTEDな試行を回数へ加えない。公開GitHubに非公開証拠をアップロードしない。

ユーザーへの表示は、認証時のみ「**次の1手**／操作する場所／参加者や設定など必須値／根拠は要点のみ／実行後に送るもの／Rule／Fallback」。STOP時は実行組み合わせを出さず、直す必要がある最小の確認だけを返す。ゲーム側の実行操作が人間の承認に当たり、追加の形式的なチャット承認を常設しない（契約整合はコード・テストで確認する）。

## 4. 実装所有者・導線

- `current_observation.py` と既存 P5/非公開 evidence receipt：差分だけを取り込み、同じ原本SHAを使い回す。状態変更の結び付けは `live_state_engine.py` の正本 replay/after_event_id を使用。
- `navigator_step.py`：単一選択済みの `development_plan` だけを比較する構造を修正。各候補へ根拠付きの多軸評価を返し、真の対抗候補の不足だけを優先順位の検討対象とする。

- `next_action.py` + `check_reply.py`：現行のsource-receiptと完全一致返信検証を維持して、試合・活動・回復の安全な応答表現を必要な順に追加。署名なし文章をSAFEとは扱わない。まず実機のTRAINを通し、次の行動種別を試す。
- **実行面の問題（最初に解く）**：今のChatGPT一般チャット + 公開GitHub P4 enum bridgeだけでは、非公開画像と `private-context` をPythonに渡して `safe_reply_check=PASS` を取得できない。現ChatGPT画面は画像を扱えるが正本Python実行面へ直結しておらず、SHORI-local Codexは正本Pythonを実行できるがiPhone/ChatGPTの画像を自動で受け取れるとは未確認。**P7-J0で同じ信頼境界内に入力画像・既存ロスター・Python実行・ユーザーへの返答を揃える経路を実証する**。使える既存の非公開実行経路がなければ、ユーザーにAI間の中継を求めるのではなく、所有者に最小の非公開iPhoneアップロード／Python実行連係が必要と報告し、明示的な認可前に外部ホスト・認証・保存を新設しない。GitHub公開ワークフローへraw画像や私有コンテキストは渡さない。
- 新しいアプリ/バックエンドの開発は、既存の実行面でE2Eが通り、iPhone入力経路の欠落がなお実用上の支障と確認できた場合に限定して決める（Core Policy 0th principle）。新しい安全Gateは作らない。

T4 **次の1手**：実行直後の新しい状態で、古い残高を無効化して再比較。別種行動（試合または活動、必要なら回復）が適切なら certified rendering を出し、次の操作へ進める。連続して2実機サイクルを確認。未対応の行動を勝手に認証しない。

T6 **UX基準**：同一の既存能力・タイプ・相性資料を再提出させない。各停止は一つの具体的理由と次の無消費確認だけ。通常ターンは1操作＋Fallback、別エージェントへの人手転送ゼロ。

受入れが終わるまで「普通に遊べる」とは表示しない。最初の実機を通したら同じ経路で次の手を試し、そこで新しい恒久機能の開発に逸れない。
